# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Godot 4.7 (Forward Plus, Jolt Physics) 2D roulette roguelike in the style of Balatro, pure GDScript. There is no build system, linter or test suite; develop by opening the project in the Godot editor, or run it with `godot --path .` (main scene is `scenes/intro/intro.tscn`, the intro video, which hands over to `scenes/main_menu/main_menu.tscn`). `.vscode/settings.json` points godot-tools at a Windows editor path, so adjust it locally if needed. Indentation is tabs (GDScript default).

`.github/workflows/build-windows.yml` exports the "Windows Desktop" preset (x86_64, single exe with the pck embedded) on pushes to `main` or by hand from the Actions tab, uploads it as a run artifact, then posts the download link to Discord through the `DISCORD_WEBHOOK_URL` repo secret (the step is skipped if the secret isn't set). Its `GODOT_VERSION` must match the editor version exactly, so bump it when upgrading Godot.

Prose docs live in `docs/` (it has a `.gdignore`, so Godot doesn't import it): `architecture.md` (the design as built, decisions and open questions), `scene-flow.md` (how scenes are loaded and swapped) and `debugging.md` (running scenes on their own, saves). Keep them in sync when changing those systems. The original proposal is the "Roulette run structure proposal" doc (https://claude.ai/artifact/GGBJfbtG4TACy3CQSebUXR). Terms: a **run** is a series of **tables**, each table has several **rounds** (a play phase of a few spins) with a **shop** between them, and **tickets** are our version of Balatro's jokers.

## Architecture

Scenes live in `scenes/<name>/` with their script alongside.

### Run structure

- **Game** autoload (`scenes/game/game.gd`) holds the current run as `Game.run` and starts, saves (`user://run.tres`), loads and ends runs. `new_run(seed, false)` makes a throwaway run that never saves; scenes use it when run on their own (F6) so they don't overwrite the real save. The editor only picks up autoload changes made outside it after Project → Reload Current Project.
- **RunState** (`scenes/game/run_state.gd`) is a Resource holding everything that outlives a phase: money, tickets, pockets, the step queue, the current step and round, and a seeded `rng`. It's saved whole with `ResourceSaver`, so anything that must survive a save is an `@export`. `rng.state` is copied into `rng_state` on save. All gameplay randomness goes through `run.rng`.
- **Base values are never overwritten by effects.** Effective values (spins per round, score, prices) are computed through `Modifiers` each time.
- **Steps** (`scenes/run/steps/`): a run is a queue of `RunStep` Resources (`RoundStep`, `ShopStep`). Each names its `phase_scene` and handles its own outcome in `on_finished`. Steps loaded from `.tres` are shared by the resource cache, so `duplicate(true)` them before queuing.
- **Runner** (`scenes/run/run.gd`, `run.tscn`) plays steps one at a time with `await`, saving after each. It resumes `current_step` if a loaded save has one. `RunGenerator.next_table()` builds each table's steps (layout and difficulty live there); an empty result means the run is won.
- **Phase contract**: every phase scene has `setup(run, step)`, called before it enters the tree, and `signal finished(result)`. Phases never decide what comes next.
- **Modifiers** (`scenes/modifiers/`): tickets (`Ticket`), boss rules and other effects extend `Modifier` and override only the hooks they need (`modify_spins`, `modify_score`, `modify_price`, `on_event`). `Modifiers` (static) runs them in a fixed order: tickets in `run.tickets` order (order is a mechanic), then the current `RoundStep.modifiers`. Game rules go through this loop; signals are only for UI, sound and animation. Event names and args are listed at the top of `modifiers.gd`.
- **Scoring** is a placeholder: a spin's `SpinContext` holds one `ScoreContext` per placed bet. Each carries `points × mult` through the modifiers, starting from that bet's chips and base mult, and records a `trace` for the wheel view to play back. `modify_score` runs once per winning bet; effects on the whole spin (pass tickets) go through `SpinContext.add_mult`/`multiply_mult`, which change every bet.
- **Cards are views, not things.** A `Card` (`scenes/card/`) shows one `Modifier` (a ticket now, consumables later), which owns the data and behaviour and lives in the run. The card and its tooltip only read `display_name`, `icon`, `get_description()` and `get_kind_name()`, listen to `triggered`, and never branch on the item's type. If it changes the run, it doesn't go in Card: what interacting with a card means belongs to whatever holds it (`CardContainer`'s drag to reorder reports `order_changed`; the play phase turns that into ticket order). The tooltip is one shared `Tooltip` autoload (`scenes/tooltip/`, a CanvasLayer) that cards call `show_for`/`hide_for` on. See `docs/architecture.md`.
- **Pause menu** (`scenes/pause_menu/`) lives in `run.tscn` with Process Mode Always so it hears Esc while unpaused; everything else in the run is Pausable.
- **Settings** autoload (`scenes/settings/settings.gd`, listed first) holds player preferences in a `ConfigFile` at `user://settings.cfg`. Add a setting to `DEFAULTS` and handle it in `_apply`; read it with `get_value(section, key)`, change it with `set_value`, which saves, applies and emits `changed`. Preferences only: run options belong in `RunState`. Volumes drive the `Music`/`SFX` buses in `default_bus_layout.tres`. The settings screen (`scenes/settings_menu/`) is instanced in the main menu and the pause menu; it's display only and talks to `Settings` directly.
- **Animation speed** (1x/2x/4x) is `Settings.animation_speed()`, read when an animation starts: pass it to the tween's `set_speed_scale`, or divide waits by it. The wheel spin and the bet-row score reveal use it; UI motion (view slides, cards, menus) doesn't. **Whenever you add or change an animation, decide whether it should follow the speed and tell the developer which you chose.** Gameplay the player waits through (spins, scoring, payouts) usually should; UI motion usually shouldn't. Keep the list in `docs/architecture.md` (Settings) up to date.

### Play phase

`scenes/play/play.tscn` is one round. Round progress (`spins_left`, `spin_profit`, `money_earned`, and the `bets` placed for the next spin) lives in `run.current_round` (`RoundState`), not in `play.gd`, so it's saved after every settled spin and bet change, and a save resumes mid-round.

- **Two views** that slide sideways between each other: `BettingView` (`scenes/betting_view/`: money, required and current profit and rolls remaining as `StatDisplay`s, the table of `BetSpot`s, the row of `Chip`s to drag onto it, tickets, consumables, and a `SideTab` on the right edge to go to the wheel) and `WheelView` (`scenes/wheel_view/`: a `SideTab` on the left edge back to betting, tickets, a `BetRow` per bet (`bet_row.tscn`), whose mult counts up live and which are revealed as hits or misses one by one once the ball lands, the wheel and its spin button). Views are display only: they emit signals (connected in `play.tscn`) and expose `show_*` methods, and `play.gd` holds every rule. Both views stay loaded; switching moves the views themselves (not a camera) inside the clipping `Views` Control: `play.gd` tweens `_view_position` (0 betting, 1 wheel) and lays both views out from it every frame in `_place_views`, so a slide can be reversed mid-way. Details in `docs/scene-flow.md`. Going back to betting is blocked while the wheel spins.
- **Money and vouchers**: money is for betting only. A chip costs its value when dropped (unaffordable drops are ignored), clearing a bet refunds it, and a spin pays its score into `run.money`. Money carries between a table's rounds and resets to the previous table's last required profit at the next table (`RunGenerator.next_table`); surplus is discarded. A round is won when `RoundState.profit()` (payouts minus stakes, plus pass-ticket money) reaches `RoundStep.required_profit`, shown as "Required Profit" next to "Current Profit". No money and no bets on the table loses the run. `run.vouchers` (shown as `assets/textures/voucherSymbol.png` then the amount, as BBCode from `Game.voucher_text` for a `RichTextLabel`; `Label`s and `Button`s can't show it) are earned at 2 per spin left on a won round and are what the shop and ticket selling use.
- **Bets**: chips dropped on a spot join one `PlacedBet` per `Bet.key()`, which keeps each chip as a `PlacedChip` (`value`, `tier`) rather than a total; right-clicking a spot clears it. A spin needs at least one bet and uses them all up. Chip values are `play.gd`'s `CHIP_VALUES` (a placeholder until chips are tied to money), and a chip's tier is its index there.
- **Table** (`scenes/bet_table/`): `BetTable` is a custom Container that builds a `BetSpot` per bet (zero, the numbers, `DozenBet`s, then `HalfBet`, `ParityBet` and `ColourBet` along the bottom) and lays them out as square tiles sized to fit, on a 13-column grid (zero's column half width) with white borders, rounding the corners on the outside of the grid (zero's more). Looks come from `TableStyle` (`table_style.tres`): a `BetTileStyle` per pocket colour (each can override the font and size), the default font and the line, all given at a 141.5px reference tile and scaled to the actual tile. Number tiles take their pocket's colour through `show_pockets(run.pockets)`, so recoloured pockets recolour the table.
- **Chips** (`scenes/chip/`): `Chip` (`chip.tscn`) is the draggable chip, `ChipStack` (`chip_stack.tscn`) draws a bet's chips on its `BetSpot` grouped by tier, and `ChipSet` (`chip_set.tres`) holds one texture per tier. The textures there are placeholder gradients until the real art is assigned.
- **StatDisplay** (`scenes/stat_display/`) is the reusable boxed readout: a Silkscreen `title` above a Press Start 2P `value` (after an optional `prefix`, such as "$") padded with leading zeros to `digits` wide. The zeros and the number are separate labels so they're styled apart; all the looks are in `stat_display.tscn` (the box and its drop shadow are the panel's StyleBoxFlat), and it's `@tool` so it previews in the editor.
- **SideTab** (`scenes/side_tab/`) is a `Button` stuck to the left or right screen edge (`side`) for switching views: rounded on the side facing the middle, flat and unstroked against the edge, with its `title` turned to run up the tab. The box is built in the script so it mirrors; the title's font and shadow are in `side_tab.tscn`.
- **Tickets** are one shared `CardContainer`, which `_place_views` moves between the views' `ticket_slot` Controls, so it glides between them during a slide.
- **HUD** (`CanvasLayer`) is the overlay above both views: the round result and its Continue button, plus `show_pass(pocket)`, a throwaway visualisation that pops the passed number in the right third of the screen and fades it out.
- **Audio** is an autoload singleton (`Audio`, `scenes/audio/audio.gd`): a pool of 8 `AudioStreamPlayer`s on the `SFX` bus behind `Audio.play_sfx(stream, volume_db, pitch_scale)`.
- **Wheel is rendered via a SubViewport**: `RouletteWheel` is instanced inside `Play/SubViewport`, and the `WheelOutput` TextureRect in `WheelView` displays that viewport's texture (`play.gd` hands the viewport over with `set_wheel`). The round SPIN button is in the SubViewport too, so the shader bobs and shadows it with the wheel; `set_wheel` sizes it over the hub (`RouletteWheel.hub_radius()`), and `WheelOutput` forwards mouse events into the viewport with `push_input` (a SubViewport outside a SubViewportContainer gets no input). The viewport lays out at a fixed 600×600 design size (`size_2d_override`, stretched) and `WheelView` sets its render `size` to the screen pixels `WheelOutput` covers, so it stays sharp; everything in the wheel (radii, the button and its font size, the shader's pixel offsets via its `design_size` uniform, forwarded clicks) is in design pixels, never `viewport.size`. `wheel_shader.gdshader` is applied to that TextureRect. It adds a drop shadow (cast from pixels that differ from `background_color`) and a vertical "bob" effect, so the wheel's transparent background must match the shader's `background_color`. `wheel_behaviour.gd` centres itself on the SubViewport's size.
- **RouletteWheel** (`wheel_behaviour.gd`, root) owns the spin, guarded by `is_spinning`. See "Spin and ball" below. `play.gd` gives it the run's pockets (`set_pockets`) and RNG (`rng`). It emits `pocket_passed(index, pocket)` for every pocket the ball enters (including the landing one) and `spin_finished(index, pocket)` when everything has settled. Passes drive the bet rows, the HUD popup and the tick sound, which is rate-limited (35ms, deliberately not scaled by the animation speed) with a pitch that rises per tick played in the spin; modifiers get every pass through `Modifiers.notify`, not the rate-limited sound.
- **Pockets** are `Pocket` Resources (`scenes/wheel/pocket.gd`: `number`, `colour`, `weight`), owned by `run.pockets`. `Pocket.european_layout()` returns a fresh set each call. Refer to a particular pocket by object, not index, since indexes shift when pockets change.
- **WheelVisual** (`draw_wheel.gd`) is a `@tool` node that draws the wheel entirely in `_draw()`: segments are polygons, with optional UV-mapped `segment_texture` (`texture_coverage` controls horizontal span), plus borders, rotated number labels and the hub. Pocket 0 starts at the top (-PI/2) and goes clockwise, in `pockets` array order. Its `pockets` defaults to the European layout so it previews in the editor. Colours come from the `COLOURS` constant, keyed by `Pocket.colour`.

### Spin and ball (`wheel_behaviour.gd`)

- **The winner is chosen first**, by `pick_winning_index()`, using each pocket's `weight` (0 means it can never win). The animation is then built to land the ball on that pocket, so mutating pockets (add, remove, reorder, reweight) just works. Don't change pockets mid-spin: targets are computed at spin start, so weight changes only affect the next spin.
- **The ball's angle is relative to the wheel** (`_ball_angle`), and the ball sprite is positioned each frame at `wheel.rotation + _ball_angle`. Once the relative angle stops changing the ball rides the wheel for free, and the wheel's own rotation never affects where it lands. The target angle uses `fposmod` to pick the shortest gap to the pocket, then adds `ball_turns` laps. `ball_turns` is the wheel's turns plus a few extra so the ball runs against the wheel in world space.
- **Pass detection** counts an unwrapped step (`_ball_step()`) and steps through every pocket crossed since last frame, because the ball crosses several pockets per frame early on.
- **Tween timeline**: wheel windup (pulls back against the spin), then the ball launches. Ball angle (quint ease-out, `spin_duration`) and ball radius (out to the rim, wait, then drop to the hub with `TRANS_BOUNCE`) are separate tweens. The wheel's spin is one continuous curve in `_set_wheel_spin` (ease-out to slightly past the target, then eased back onto it) that finishes when the ball stops bouncing (`ball_drop_time + ball_drop_duration`), so it is not driven by `spin_duration`. The ease-out ends at zero velocity exactly where the return starts. A high `wheel_ease_power` makes the wheel look stopped for a moment before the return.
- Timings, turn ranges (`wheel_turns_*`, `ball_extra_turns_*`), radii, windup and overshoot are all exports on the root node. The timings are at 1x: all three tweens run at `Settings.animation_speed()`. `debug_freeze_wheel` skips the wheel tween so only the ball moves.

### `draw_wheel.gd` redraw mechanism

Exported properties in `_DRAW_PROPERTIES` trigger `queue_redraw()` through a custom `_set()` override, so edits in the inspector update live in the editor. When adding a new exported property that affects drawing, add it to `_DRAW_PROPERTIES`. The override deliberately ignores sets while not in the tree (the scene entering the tree redraws once), and uses `_setting_draw_property` to avoid recursion. `pockets` isn't exported: its setter redraws, and connects to each pocket's `changed` signal so editing a pocket redraws too.

## Conventions

- Assets go in `assets/` (`fonts`, `textures`, `video`, `audio/{music,sfx}`); `addons/` is currently empty. Do NOT attempt to read anything within `/assets` through any tools - if you would need to make changes, instead explain them to the developer so they can make them for you.
- The intro video is Ogg Theora (`.ogv`, the only format Godot plays natively) in `assets/video/`, rendered from After Effects to a lossless master and converted with ffmpeg. Set it as the `Video` node's stream in `scenes/intro/intro.tscn`.
- Commit the `.uid` files Godot generates next to scripts and shaders. Don't commit `.godot/`.
- Always update `docs/` when making changes to the project, once you're done.
